# Human review workflow (online + owner login)

Queued harvest proposals are reviewed on a public board. **Only the repository
owner (`NZA-93`)** can accept identity decisions into the seed. Community
comments help authoring but stay on a separate layer from editorial voice.
Signed editorial is **not** this board: Critic authors and lands it
([`CRITIC.md`](CRITIC.md)).

## Layers

| Layer | Path | Who writes | Enters scores? |
|---|---|---|---|
| Owner decisions | `proposals/review-decisions.json` | Owner (`CODEOWNERS`) | No — facts (mbid) only after apply |
| Community notes | `data/community/comments.json` | Anyone via issue/PR | **Never** |
| Signed editorial | `data/editorial/` | **Critic** (named editorial role) | Judgement (ADR-002). Lands on `main` / Pages; no human merge babysit. Developer may ship the Critic PR |
| Statements | `data/statements/` | Human ratification only | Assessment facts |

## Online board

After `make site` / publish:

`https://nza-93.github.io/Classical-Music-Recording-Catalogue-/review/`

Shows accept-eligible / needs-review / wrong-work buckets, MusicBrainz links,
and amber **community** notes. Regenerated by `site/build_review.py`.

### Needs-review identity rows (244)

Each needs-review row is decidable without inventing musicology. Side by side:

| Shown when present | Omitted when absent (not repeated as boilerplate) |
|---|---|
| Work title, seed catalogue | Soloist roles, venue, release MBID |
| Conductor, orchestra, soloists string | — |
| Seed year + MB first-release (labelled as **release-year proxies**, not session) | Session year, unless MB title/disambiguation has an explicit recording-year token |
| Fassung / completeness / live-studio | Those three, unless a token exists in the harvest/WS/2 hit |
| Seed label | Seed catno; MB label / catno / barcode |
| Release-group MBID + link | — |
| **Match confidence** (MusicBrainz search 0–100, never stars / never a verdict) | — |
| **Why it missed auto-accept** (from `review_flags` + real year/title diffs only; language variants such as Symphony/Symphonie No./Nr. are not a work conflict) | Invented reasons |
| Remake siblings (same **work id**, different year) | Cross-composer nickname matches (“Fifth”) |
| Amber community notes, pack id | — |

A find box filters the board (Kleiber, Beethoven 5, `bach/john`…). There are **no** public accept/reject/defer buttons. Owner path: edit `review-decisions.json`, then Actions **Review apply** (owner actor) or `make review-apply`. Identity apply writes the release-group MBID only.

Accept criteria that can be checked from payload are visible as pass / conflict.
Fassung / completeness / session / live-studio criteria appear only when a value
is present to compare — empty fields are omitted from the row, not printed 244
times as “absent Fassung”. The board does **not** auto-write `defer` into
`review-decisions.json`.

Sort: why-missed severity first (title → compilation → date → confidence),
then work prominence (seed order).

Citation tasks stay in the tally only — **off** identity rows.

Field-by-field inventory for the 244:
`proposals/review/PAYLOAD_GAPS.md` (regenerated with the board).

### Owner accept checklist (visible; not auto-applied)

Before `decision=accept`, confirm on the board (or by opening MB):

1. Same work + Fassung + completeness (Fassung/completeness often blank → prefer defer)
2. Same principal artists / roles (MB artist-credit currently payload-absent)
3. Same session year (field often blank; release-year proxies may conflict)
4. Not an excerpt/sampler unless the seed is
5. Live vs studio agrees or both unknown (often blank)
6. MBID is this performance, not a VA box
7. Fill `by` + `date` on the accept row

## Owner path (your personal GitHub login)

```bash
make review-queue          # refresh packs + decisions template
# edit proposals/review-decisions.json → accept | reject | defer
# fill by: (your initials) and date: on each accept
make review-apply-dry      # see what would land
make review-apply          # write mbids into data/seed.json
make site                  # rebuild catalogue + review board
```

Or, signed into GitHub as **NZA-93**, run Actions → **Review apply**
(`.github/workflows/review-apply.yml`). Non-owner actors are refused.

`make review-apply` on a local clone is **not** login-gated (trusted-owner
tooling). The hard remote gate is the Action (`github.actor == repository_owner`)
plus `CODEOWNERS` on `review-decisions.json`. Do not run apply on a shared
machine as someone else.

Wrong-work rows are pre-rejected and remain unforceable in `apply.py`.

## Community path

1. Open **Community review comment** issue template, or comment from the board.
2. Workflow opens a PR into `data/community/` only.
3. Owner merges the PR when the note is useful.
4. Notes appear on the review board; they are **not** editorial and must not
   be copied into `data/statements/` or signed entries by harvest/seed agents.
   Critic may read them as briefing; Critic still writes the entry.

## What this does not do

- Invent interpretation / sound scores  
- Invent musicological values for empty harvest fields (Fassung, completeness, session year, live/studio, …)  
- Scrape review sites  
- Let community write `data/editorial/` or `data/statements/`
- Gate Critic signed-editorial landings on a human merge (see [`CRITIC.md`](CRITIC.md))  
- Auto-apply without an `accept` decision from the owner  
- Auto-write `defer` into decisions when fields are absent (absence is visible only)  
- Put citation tasks on identity rows
